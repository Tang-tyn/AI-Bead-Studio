# DEVELOPMENT_RULES.md — 开发流程规范

> 所有开发人员（含 AI 编程助手）必须严格遵守本规范。

---

## 1. 页面开发流程（强制）

每个新页面的开发必须按以下 7 步流程执行：

```
需求分析
   ↓  明确页面功能、入口、交互流程
UI 布局设计
   ↓  参照 docs/UI_DESIGN.md 设计布局
   ↓  输出：页面的 ASCII 布局图
组件拆分
   ↓  识别可复用的子组件
   ↓  输出：组件树结构
状态设计
   ↓  确定 @State 变量、ViewModel 类
   ↓  输出：状态清单 + 数据流向
ArkTS 实现
   ↓  先写 ViewModel → 再写 View
   ↓  遵守 CLAUDE.md 编码规范
编译验证
   ↓  DevEco Studio 编译通过、无 CompileArkTS 错误
UI 优化
   ↓  对照 UI_DESIGN.md 检查：布局/颜色/动画/间距
```

### 1.1 设计先行原则
- **禁止**：不画布局直接写代码
- **要求**：每个页面在编码前，先输出 ASCII 布局图 + 组件树
- **目的**：避免反复修改 UI 结构造成浪费

### 1.2 逐层实现原则
- 先 ViewModel（业务逻辑 + 状态），后 View（UI 渲染）
- ViewModel 完成后应可独立进行逻辑测试
- View 只绑定状态和转发事件

## 2. 禁止事项

### 2.1 代码质量
| 禁止行为 | 说明 |
|----------|------|
| 直接生成临时 UI 作为最终页面 | 当前占位页面仅用于功能验证，后续须按设计规范重写 |
| 没有设计说明直接写页面 | 必须先有布局方案 |
| 随意创建重复组件 | 先检查 `view/components/` 是否有可复用的 |
| 页面直接调用 Service | 必须通过 ViewModel 中转 |
| View 层包含业务逻辑 | 数据处理、计算、判断一律在 ViewModel/Service |
| 使用未验证的 API | 必须先在 REFERENCES.md 和官方文档确认 |

### 2.2 架构纪律
| 禁止行为 | 说明 |
|----------|------|
| View 直接 import Service | 破坏 MVVM 分层 |
| ViewModel import ArkUI 类型 | 引入 `@kit.ArkUI` 等 UI 依赖 |
| Service import ViewModel | 造成循环依赖 |
| 硬编码颜色/字号 | 必须用 `$r('app.color.xxx')` / `$r('app.float.xxx')` |
| 硬编码字符串 | 必须用 `$r('app.string.xxx')` |

### 2.3 版本问题
| 禁止行为 | 说明 |
|----------|------|
| 使用其他 SDK 版本的示例代码 | 只参考 API 24 |
| 猜测 API 存在/参数 | 不确定时停止并报告 |
| 使用未验证的 SymbolGlyph 图标名 | 先用 Text 占位，标注 TODO |

## 3. Phase 完成标准

每个 Phase 完成后必须满足以下条件：

### 3.1 编译标准
- [ ] `CompileArkTS` 无错误、无警告
- [ ] DevEco Studio 模拟器可正常运行
- [ ] 所有新增代码无未使用的 import

### 3.2 功能标准
- [ ] Phase 计划功能全部完成
- [ ] 异常情况有处理（空数据/加载中/错误）
- [ ] 浅色/深色模式均正常显示

### 3.3 文档更新（强制）
每个 Phase 完成后必须更新以下文件：

| 文件 | 更新内容 |
|------|----------|
| `CHANGELOG.md` | 新增条目，记录本 Phase 的 Added / Changed / Fixed |
| `TODO.md` | 标记已完成任务，添加已知问题 |
| `CLAUDE.md` | 更新 Phase 状态表 |

## 4. 代码审查清单

提交代码前自检：

```
□ 所有 .ets 文件有 JSDoc 头部注释
□ 所有 public 方法有 @param / @returns 注释
□ 使用 interface 而非对象字面量类型
□ 颜色/字符串/字号通过 $r() 引用
□ @State 变量名不与内置属性冲突
□ 异步方法有 try-catch
□ 错误有用户可见的提示（非 console.error 静默处理）
□ 不使用的 import 已删除
□ main_pages.json 与实际 @Entry 页面一致
```

## 5. Git 工作流

### 5.1 分支策略
```
main         ← 稳定可编译版本
  └── develop    ← 开发主分支
       └── phase/N  ← 每个 Phase 的功能分支
```

### 5.2 提交规范
```
feat: <简短描述>        # 新功能
fix: <简短描述>         # 修复
docs: <简短描述>        # 文档更新
refactor: <简短描述>    # 重构
style: <简短描述>       # 样式调整
```

### 5.3 提交时机
- 每个小功能完成后 commit
- 每个 Phase 完成后 commit + tag
- tag 格式：`v0.1.0-phase0`

## 6. AI 编程助手专用规则

当 AI 编程助手参与开发时，必须遵守：

### 6.1 开工前
1. 阅读 `CLAUDE.md` 全文
2. 阅读 `docs/REFERENCES.md` 中相关 API 文档
3. 确认当前 Phase 目标

### 6.2 编码中
1. 先说明设计思路，再写代码
2. 每个文件输出后列出修改清单
3. 零基础解释：对关键概念加 `【知识点】` 注释

### 6.3 输出后
1. 标注修改的文件列表
2. 说明为什么这样改
3. 如有未确定项，明确列出并等待用户确认

### 6.4 禁止
1. 在不了解上下文时猜测实现
2. 脱离 CLAUDE.md 规范自行发挥
3. 在修复时顺便添加未要求的新功能
4. 修改与当前任务无关的文件
5. 使用未验证的 API
